# Decision journal — #231 N-3 delivery worker

## O — Phase 1 (survey + brief)

- **Decided:** Extend `QueueBackendInterface::drain()` with optional `?string $frequency = null` rather than adding a `drainByFrequency()` method (Reuse map default: extend over new).
- **Decided:** Digest deliveries produce ONE LogMailer invocation per recipient (not per message) — the digest IS a single email in a real-mailer replacement. Uses `mid` of the first message in the group as the log identifier; template = `digest_daily` / `digest_weekly`.
- **Decided:** Skip-with-warning (not fail) on missing Message / user during delivery — a stale queue entry must not halt the worker.
- **Decided:** New `DoNotificationsCommands` class + `drush.services.yml`. No existing drush surface in module.
- **Assumed:** message_notify's plugin manager is `plugin.message_notify.notifier.manager` and supports `createInstance('log_mailer', [], $message)` as LogMailerTest already uses.
- **Assumed:** Drush 13 attributes-based command syntax (`#[CLI\Command(name: '...')]`) is preferred; matches drush/drush:^13 in composer.json.
- **Assumed:** Immediately-frequency deliveries render one email per message (not grouped) since latency-sensitive.
- **Hedged:** Not adding a `--dry-run` flag; can be added later. Not needed for AC.
- **Evidence:** Read QueueBackendInterface (drain has no filter), EmailRenderer::render / renderEventFragments, DigestRenderer::render, LogMailer::deliver, LogMailerTest (plugin manager usage), do_notifications.services.yml (service ids), do_notifications.install (queue schema).

- **Decided:** Real `activity_post_created` Messages are created via a real post-in-a-group fixture (`createPostMessage()`, mirroring `DigestRendererTest`'s helper of the same name) rather than a stub template with no `text`, because the worker under test calls `EmailRenderer::render()`/`DigestRenderer::render()`, which read the template's real token-replaceable text — a template with no rendering surface would not exercise the real rendering path this story wires in.
- **Decided:** The worker is invoked via `\Drupal::service('do_notifications.deliver_commands')->deliver(['type' => $type])` — the Drush 13 option-array convention — rather than shelling out to the `drush` binary. The class under test is the command's own logic; Drush's argument-parsing layer is out of scope for this story and not worth the process-invocation cost in a kernel test.
- **Decided:** `enqueue()` on the real `do_notifications.queue` service (not a raw DB insert) is used to seed every test's starting queue state, so each test also incidentally re-validates the dedup/tuple contract already pinned by `DatabaseQueueBackendTest`/`SubscriptionRouterTest` still holds under this worker's usage pattern, at zero extra cost.
- **Decided:** `testDeliverSkipsMissingMessageWithWarning` asserts watchdog `severity = 4` (`RfcLogLevel::WARNING`) specifically, not just "a row exists" — pins the brief's AC #5 "logs a warning" wording precisely, distinguishing it from an `info`-level delivery log row.
- **Hedged:** Did not author a unit-tier test for any sub-piece (e.g. "grouping helper groups by uid") because no such helper is named in the brief/reuse map — the grouping behavior is only observable through the worker's end-to-end drain-then-deliver flow, so a kernel test is the cheapest sufficient tier, not a redundant one layered on top of a cheaper unit test.

## F — Phase 5 (implement GREEN)

- **Decided:** Registered `do_notifications.deliver_commands` in `do_notifications.services.yml` in ADDITION to `drush.services.yml`, not only `drush.services.yml` as the locked plan specified. Traced `vendor/drush/drush/src/Runtime/LegacyServiceInstantiator.php`: Drush 13's `drush.services.yml` mechanism is a one-way reader of Drupal's container (instantiates classes via reflection into its OWN internal array for Drush's own command registration) — it never writes back into Drupal's real service container, so `\Drupal::service('do_notifications.deliver_commands')` (what T's kernel test calls, per its own documented Drush-13-testing convention) can never resolve a service that exists only in `drush.services.yml`. Verified by reading `LegacyServiceInstantiator::instantiateServices()`/`create()`/`instantiateObject()` line by line — no `$container->set()` call anywhere in the class.
- **Decided:** `$notifierManager` constructor argument is nullable, referenced as `'@?plugin.message_notify.notifier.manager'` (optional DI reference), not a hard `'@...'` reference. A hard reference broke container compilation for `DatabaseQueueBackendTest`/`DigestRendererTest`/`EmailRendererTest` — all three enable `do_notifications` without enabling `message_notify` (Symfony validates every registered service's references at compile time regardless of instantiation). `deliver()` fails fast with `\RuntimeException` if genuinely NULL at call time (only reachable on a mis-provisioned site missing `do_notifications`'s own declared `.info.yml` hard dependency on `message_notify`).
- **Decided:** `--type=all` drains the ENTIRE queue in one `drain(NULL)` call, then groups by `frequency` in-process, rather than three separate `drain('immediately')`/`drain('daily')`/`drain('weekly')` calls — avoids a 3-drain race window against a concurrent enqueue; the interface already returns each entry's own frequency, so grouping after is free.
- **Decided:** Digest `mid` identifier uses the FIRST SURVIVING message id (first entry, in enqueue order, whose Message actually loads), not unconditionally the first entry's mid — a recipient whose very first queued entry references a since-deleted Message must not have their digest's log identifier point at a message nothing was rendered for.
- **Decided:** Injected logger property renamed `$notificationsLogger` (not `$logger`) — `DrushCommands` (parent) already declares a non-readonly `$logger` via `Psr\Log\LoggerAwareTrait`; a constructor-promoted readonly `$logger` fatals with "Cannot redeclare non-readonly property ... as readonly."
- **Decided:** Added a one-line `(int)` cast to `EmailRenderer::renderEventFragments()`'s `created` value — a file NOT in the brief's "Files expected to change" list. Root cause traced fully: `Message::getCreatedTime()` reads the field item's raw `->value`, not `Timestamp::getCastedValue()` (which casts); `SqlContentEntityStorage::mapFromStorageRecords()` assigns a freshly-`->load()`-ed entity's field value directly from the PDO-fetched row with no cast of its own (read the core method body to confirm); MySQL/MariaDB's PDO driver commonly returns an int-columned value as a numeric string. Every pre-#231 caller of `renderEventFragments()` only ever passed an in-memory Message whose `created` was just set via `setCreatedTime()`/`applyDefaultValue()` (a real int, never DB-round-tripped) — this story's worker is the first caller to `getStorage('message')->load($mid)` a Message the queue only knows by numeric id, which is what exposed the gap (`TypeError: gmdate(): Argument #2 ($timestamp) must be of type ?int, string given` inside `DigestRenderer::groupByDay()`). Fixed at the one shared source both `EmailRenderer::render()` and `DigestRenderer::collectFragments()` funnel through; verified `EmailRendererTest`/`DigestRendererTest` both still pass unmodified (casting an already-int value is a no-op).
- **Hedged:** Did not add a `--dry-run` flag (matches O's Phase-1 hedge; not needed for any AC).
- **Evidence:** `vendor/drush/drush/src/Runtime/LegacyServiceInstantiator.php` (full read, confirmed no container write-back), `vendor/drush/drush/src/Boot/DrupalBoot8.php::addDrupalModuleDrushCommands()` (confirmed `drush.services.yml` is only read during Drush's own bootstrap, entirely separate from `\Drupal::getContainer()`'s compiled container), `vendor/consolidation/annotated-command/src/Attributes/{Command,Option}.php` + `vendor/drush/drush/src/Commands/core/CacheRebuildCommands.php` (confirmed exact Drush 13 attribute syntax), `web/core/lib/Drupal/Core/Field/Plugin/Field/FieldType/{CreatedItem,TimestampItem}.php` + `web/core/lib/Drupal/Core/TypedData/Plugin/DataType/{Timestamp,IntegerData}.php` + `web/core/lib/Drupal/Core/Entity/Sql/SqlContentEntityStorage.php::mapFromStorageRecords()` (full trace of the int/string gap), `docs/groups/modules/do_notifications/tests/src/Kernel/DigestRendererTest.php` (confirmed its `createPostMessage()` always calls `setCreatedTime()` explicitly, unlike T's new `DeliveryWorkerTest::createPostMessage()`), `web/core/modules/datetime/datetime.services.yml` (confirmed `'@?service_id'` optional-reference syntax is an established core convention).
