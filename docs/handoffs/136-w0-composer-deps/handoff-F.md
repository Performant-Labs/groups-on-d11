## Design decisions

- **Environment used: host `composer`, not `ddev composer`.** This worktree's `.ddev/config.yaml`
  (`name: pl-groups-on-d11`) collides with an already-registered, differently-located DDEV
  project (`~/Sites/pl-groups-on-d11`, a separate local checkout of the same repo). `ddev start`
  in this worktree failed (`a project (web container) in exited state already exists for
  pl-groups-on-d11 that was created at /Users/.../Sites/pl-groups-on-d11`). Renaming/unlisting
  that other project would be a change to shared local DDEV state outside this issue's scope, so
  I did not touch it. I used host `composer` (2.8.10) instead, per the brief's explicit fallback
  ("if DDEV isn't usable in this sandboxed environment, fall back to host composer").
- **`--ignore-platform-req=php` was required and is safe.** Host PHP is 8.3.31; the project's
  `.ddev/config.yaml` pins `php_version: "8.4"` (the real target runtime, e.g. CI's
  `PHP_VERSION: '8.4'` in `.github/workflows/test.yml`). Without the flag, composer's resolver
  rejected on `doctrine/instantiator 2.1.0` (a `drupal/core-dev` → `phpspec/prophecy` transitive
  dev-dependency) requiring PHP `^8.4`. I confirmed via `git stash` that this exact same
  PHP-8.3-vs-8.4 platform rejection reproduces on unmodified `main`/base commit `c18f417` too —
  i.e. it is a pre-existing host/target PHP mismatch, not something introduced by the 5 new
  packages or evidence of an incompatibility with them. The actual package resolution itself
  (all 5 new packages + `drupal/group: 4.0.x-dev` + `drupal/core-recommended: ^11.4`) succeeded
  cleanly once the unrelated dev-tooling PHP-version gate was bypassed — this is exactly the
  kind of platform-req override that's safe because the target environment (DDEV, CI) genuinely
  runs PHP 8.4/8.5 and will resolve identically without the flag.
- **Reverted composer's scaffold-file touches (`web/.htaccess`, `web/index.php`,
  `web/robots.txt`, `web/update.php`, `web/example.gitignore`) and deleted two newly-generated,
  previously-untracked scaffold files (`web/.gitignore`, `web/autoload_runtime.php`).** Running
  `composer require`/`composer install` invokes `drupal/core-composer-scaffold`, which
  re-materializes these files from the (unchanged, still 11.4.4) `drupal/core` package assets.
  The tracked scaffold files' on-disk content differed slightly from what the installed
  `drupal/core` package would now generate (confirmed core version itself did NOT change:
  11.4.4 before and after), and two files (`web/.gitignore`, `web/autoload_runtime.php`) don't
  exist in the repo at all. None of this is in scope per the brief ("No other files. No
  `.info.yml` enables, no config, no seed script changes" / verification item 3: "confirm ONLY
  `composer.json` and `composer.lock` changed"), so I reverted/removed all of it rather than
  leave it in the diff or silently commit-worthy drift. This is standard, expected composer
  behavior on any dependency change and not something Wave 1-4 stories need to worry about.
